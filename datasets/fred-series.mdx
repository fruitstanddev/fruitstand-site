## Schema

The core observations table is analytic‑ready, one row per series per date:

| Column | Type | Description |
| --- | --- | --- |
| `series_id` | `varchar` | FRED series identifier (e.g. `CPIAUCSL`) |
| `series_name` | `varchar` | Human‑readable series name |
| `date` | `date` | Observation date |
| `value` | `float` | Observed value |
| `units` | `varchar` | Units of measurement |
| `frequency` | `varchar` | Observation frequency (daily, monthly, quarterly, etc.) |
| `seasonal_adjustment` | `varchar` | Seasonal adjustment method |
| `output_type` | `varchar` | FRED output type |
| `aggregation_method` | `varchar` | Aggregation method used |
| `last_updated_at` | `timestamp` | Last time FRED updated this observation |

```sql
select series_id, series_name, date, value, units, frequency
from fred.fred_series_observations
where series_id = 'CPIAUCSL'
order by date desc
limit 3;
```

## Data Ingestion

Data is ingested into Snowflake with best practices in mind.

<Steps>
  <Step title="Logical layers">
    Source API → ephemeral local parquet → S3 dated folder (raw snapshot by entity type) → Snowflake staging tables → curated Snowflake final tables/views.
  </Step>
  <Step title="Incremental ingestion">
    Daily updates are pulled from the API; downstream assets filter only series whose updates exceed what observations already hold (incremental refreshing).
  </Step>
  <Step title="Fine‑grained file layout">
    One parquet per series per run supports selective reprocessing, late arrivals, parallelism, and lifecycle policies.
  </Step>
</Steps>
